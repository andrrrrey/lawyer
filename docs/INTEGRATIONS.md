# Интеграции Lawyer

Доступы задаются в разделе **«Настройка → Интеграции»** или через `.env`.
Сохранённые через интерфейс значения имеют приоритет. Секреты не должны
попадать в репозиторий и журналы приложения.

## Источники

| Источник | Количество | Назначение |
|---|---:|---|
| Bitrix24, коробочная версия | 1 | сделки, воронки, сотрудники, задачи и стадии |
| Bitrix24, облачная версия | 1 | сделки, воронки, сотрудники, задачи и стадии |
| Яндекс Директ + Метрика | 3 | отдельная связка на ЮО, ЦСВ и УрПАСЭ |
| 1С:УНФ | 1 | единственный источник фактических поступлений |
| LLM | 1 | необязательная интерпретация уже рассчитанных данных |

Calltouch и МойСклад в текущей конфигурации не используются и в интерфейсе
подключений не показываются. Telegram в текущий этап не входит.

## Переменные окружения

- Bitrix24: `BITRIX_BOX_WEBHOOK_URL`, `BITRIX_BOX_INBOUND_TOKEN`,
  `BITRIX_CLOUD_WEBHOOK_URL`, `BITRIX_CLOUD_INBOUND_TOKEN`.
- ЮО: `YANDEX_UO_OAUTH_TOKEN`, `YANDEX_UO_DIRECT_LOGIN`,
  `YANDEX_UO_METRIKA_COUNTER_ID`.
- ЦСВ: `YANDEX_CSV_OAUTH_TOKEN`, `YANDEX_CSV_DIRECT_LOGIN`,
  `YANDEX_CSV_METRIKA_COUNTER_ID`.
- УрПАСЭ: `YANDEX_URPASE_OAUTH_TOKEN`, `YANDEX_URPASE_DIRECT_LOGIN`,
  `YANDEX_URPASE_METRIKA_COUNTER_ID`.
- 1С: `ONEC_ENDPOINT`, `ONEC_USERNAME`, `ONEC_PASSWORD`.

## Bitrix24

Технические ключи `box` и `cloud` нужны только для предотвращения коллизий ID.
Они не являются тенантами или отдельными CRM-порталами в пользовательском
интерфейсе. Соответствие `источник × ID воронки → юрлицо × профиль SLA`
редактируется на странице **«Настройки → Воронки»**.

При каждой быстрой сверке вместе с изменёнными сделками инкрементально
обновляются история стадий и CRM-активности типов «звонок»/«встреча». Полная
сверка заполняет историю за всё окно дашборда. Из этих фактов рассчитываются
`first_contact_at`, `stage_entered_at`, `last_activity_at` и наличие звонка;
повторная загрузка идемпотентна по ID активности и комбинации стадии/времени.
Недоступность одного из REST-методов фиксируется отдельно и не удаляет ранее
загруженные факты.

## 1С:УНФ

Для боевого запуска используется endpoint из ТЗ по HTTP и Basic Authentication.
Запрос выполняется методом `POST`; период передаётся JSON-телом в полях
`ДатаНачала` и `ДатаОкончания` в ISO-формате (`ГГГГ-ММ-ДДT00:00:00`).
Ответ должен быть JSON-массивом либо объектом с массивом в `data`, `result`,
`rows` или `value`. Поддерживаются поля регистратора, организации, контрагента,
договора, статьи ДДС, суммы, `Код_BTX` и `Тип_BTX`, включая вложенную структуру
реального ответа сервиса 1С.

Правила обработки:

- юрлицо определяется по точному ИНН организации;
- статья ДДС сопоставляется по точному наименованию после удаления пробелов по краям;
- внутренние переводы между тремя собственными ИНН исключаются;
- неизвестные юрлица и статьи сохраняются в журнале, но не входят в выручку;
- связь со сделкой выполняется по `Код_BTX`/`Тип_BTX` и техническому источнику CRM;
- деньги сохраняются с точностью до копеек (`NUMERIC(18,2)`).

## Запуск синхронизации

```bash
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml exec api python -m app.services.ingest
```

Перед переключением `DATA_SOURCE=real` заполните ИНН трёх юрлиц, сопоставьте
воронки и проверьте каждое подключение в интерфейсе.
